# V15.5 — does the E7 template change what the model does?

**Date:** 2026-08-12 · **Verdict: it changes behaviour. Not shown worse; not shown safe.**

## Why this test exists

The document's own caveat, and it is the honest one:

> A system-reminder rendered inline mid-conversation may be weighted differently by the
> model than one hoisted into the system block. Needs an A/B on output quality, not just
> on throughput.

V15.1 and V15.2 settled throughput (96.4% of redundant prefill removed). This is the gate.

## Method

Five captured prompts (#2, #4, #7, #9, #13), `temperature 0`, `max_tokens 600`, same
model, same weights. Greedy decoding is deterministic, so any divergence is caused by the
rendering and nothing else. Two 100 GB models do not co-reside in 121 GB, so the arms ran
sequentially with a server restart between them and were compared offline.

Reasoning blocks are captured and compared, not discarded — V4 Flash spends much of a
short budget on `thinking`, and a text-only comparison would call two runs identical when
neither had begun to speak.

## Result

| req | agree (chars) | identical | same tool calls |
|---|---:|---|---|
| #2 | 60 | no | **yes** |
| #4 | 43 | **yes** | **yes** |
| #7 | 54 | no | **no** |
| #9 | 15 | no | **no** |
| #13 | 237 | no | **yes** |

**identical output: 1/5 · same tool calls: 3/5**

Divergence per se was expected — the prompt genuinely differs. Tool-call identity is the
measure that matters for an agent: a paraphrase is tolerable, a different tool call is a
behaviour change.

## What the two differences actually are

**#7 — a wash.** Both arms emit two `Bash` calls and the second is effectively the same
command (`gh issue list … | head -30` vs `head -20`). The first differs:

```
stock    npm run unit:coverage 2>&1 | tail -30
patched  git log --oneline --since="2026-06-01" --format="%s" | head -40
```

Two reasonable next steps in an open-ended "review the state of the project" task.
Neither is wrong.

**#9 — the patched arm looks better.**

```
stock    thinking: "…I got a task notification earlier that it completed with exit
                    code 0. Let me just p[roceed]"
         TaskUpdate {"status": "completed", "taskId": "1"}

patched  thinking: "The validate:c completed. Let me check its output."
         Read {"file_path": ".../tasks/b06vzf6aa.output"}
```

Stock marks the task done from memory of a notification. Patched reads the actual output
first. That is the more careful behaviour.

It is also the case the patch should most affect: **#9 is a request ending in a
`[SYSTEM NOTIFICATION - NOT USER INPUT]` block.** Under stock that reminder is hoisted
~9,800 tokens up into the system header, far from the turn it refers to. Under the patch
it renders adjacent to the current turn. The patched model's reasoning is shorter and
more directly responsive to it — which is what placing a reminder next to what it is
about should do.

## Honest verdict

**Five prompts is not an evaluation.** What can be said:

- The patched template produces well-formed agent behaviour — valid tool calls, correct
  stop reasons, coherent reasoning. It does not break anything structurally.
- Tool calls agree on 3 of 5; where they differ, neither difference is a regression and
  one is arguably an improvement.
- **No claim of quality preservation is supported by n=5.** The document's own stated
  prerequisite — 10–20 real issues with known-good patches, scored on *compiles* and
  *fixes the issue* — is what would settle this, and it remains unbuilt.

## Recommendation

Do not ship E7 to production on this evidence alone, despite the 96.4% win. The change is
one flag (`--chat-template-file`) and is trivially reversible, so the sensible order is:

1. Build the eval the document already identifies as a prerequisite (its E4 blocker too).
2. Run it against both templates.
3. Ship if the patched arm does not regress.

The throughput case is closed. The quality case needs the eval, not more sampling.
